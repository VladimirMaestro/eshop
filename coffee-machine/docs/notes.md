# Entity vs Value Object

## Entity (who)
Must have an identity
- Should have ID
- Values can change, but the object remains the same

## Value Object (VO) (what)
Doesn't have identity
- It defines only by values
- Two VOs with the same values are equal
- It is immutable

# ❓ «Ну и что? Почему это плохо?»

# 1️⃣ Всё в одном классе
### Что происходит на практике
Каждый новый фича-запрос → изменение одного и того же класса.
Со временем CoffeeMachine:
* растёт
* обрастает if
* становится страшным
* ломается при каждом изменении

⠀К чему это приводит
* ❌ Любое изменение ломает старое поведение
* ❌ Нельзя менять одну часть, не трогая другие
* ❌ Один класс знает «слишком много»
* ❌ Страшно что-то менять → код замирает

⠀📌 **Симптом**:
«Лучше не трогать, вдруг сломается»

# 2️⃣ Нет домена (всё просто числа)
### Что происходит на практике
### new Recipe(-100, 999, -5)

Система:
* принимает это
* обрабатывает
* может «сварить кофе»

⠀К чему это приводит
* ❌ Ошибки ловятся слишком поздно
* ❌ Каждое место должно перепроверять данные
* ❌ Правила размазаны по коду
* ❌ Нет гарантии корректности объектов

⠀📌 **Симптом**:
«Нужно везде проверять входные данные»

# 3️⃣ Нет архитектурных слоёв
### Что происходит на практике
UI, логика и данные **перемешаны**:
### console.log(...)
### this.waterAmountMl -= ...
### if (...)
### К чему это приводит
* ❌ Нельзя заменить UI
* ❌ Нельзя использовать логику повторно
* ❌ Нельзя протестировать логику без UI
* ❌ Всё зависит от всего

⠀📌 **Симптом**:
«Чтобы изменить вывод, нужно лезть в бизнес-логику»

# 4️⃣ Ошибки = console.log
### Что происходит на практике
### console.log('[Error] Not enough water');
### return;
Система:
* молча прекращает работу
* вызывающий код **не знает**, что произошло

⠀К чему это приводит
* ❌ Нельзя обработать ошибку
* ❌ Нельзя показать понятное сообщение
* ❌ Нельзя повторить операцию
* ❌ Нельзя написать автоматическую реакцию

⠀📌 **Симптом**:
«Ну просто не сработало, хз почему»

# 5️⃣ Состояние мутируется напрямую
### Что происходит на практике
### this.waterAmountMl -= recipe.waterAmountMl;
Любой код может:
* уменьшить
* увеличить
* обнулить

⠀К чему это приводит
* ❌ Невозможно контролировать корректность
* ❌ Нельзя отследить, где сломалось
* ❌ Инварианты легко нарушаются
* ❌ Баги появляются «магически»

⠀📌 **Симптом**:
«Иногда вода уходит в минус, но непонятно где»

# 6️⃣ Нельзя развивать систему
### Что происходит, когда просят:
* добавить Americano
* добавить UI
* добавить тесты
* добавить логирование
* добавить новый источник воды

⠀К чему это приводит
* ❌ Нужно переписывать существующий код
* ❌ Нет места, куда это добавить правильно
* ❌ Каждое изменение — риск
* ❌ Проект упирается в потолок

⠀📌 **Симптом**:
«Давайте лучше начнём с нуля»

# 🧠 Самое короткое объяснение (одна фраза)
**Этот код работает, но он не масштабируется ни по функциям, ни по пониманию, ни по изменениям.**

# 🎯 Очень сильная аналогия (советую запомнить)
Это как квартира-студия без стен. Пока ты один — нормально. Как только появляются люди — хаос.

# 🧩 Почему архитектура решает это
Архитектура:
* не про «красивый код»
* не про «паттерны»
* а про **контроль изменений**

⠀Она отвечает на вопрос:
**Где я должен менять код, когда меняется требование?**
В первом варианте ответ:
«Везде»

# 📌 Финальный ответ для начинающего
Если он спросит:
«Ну и что тут не так?»
Ты можешь ответить:
«Пока ничего. Но при первом же изменении ты потеряешь контроль над кодом.»
