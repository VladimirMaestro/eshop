# Архитектура кофемашины
*==🟢(финальное решение, Hex)==*
## Зачем вообще архитектура
**Архитектура — это не про “красивый код”. Архитектура — это про контроль изменений.**
Она отвечает на вопрос:
*Где я должен менять код, когда меняется требование?*
Если ответ — «в одном месте», архитектура хорошая. Если ответ — «везде», архитектуры нет.

## 1️⃣ Домен (Domain)
## Что такое домен
**Домен — это модель предметной области.** Он описывает **что такое кофе**, а не **как его готовить в конкретном устройстве**.
Домен — это:
* бизнес-понятия
* правила
* инварианты
* значения и их смысл

⠀В коде это:
* Water
* CoffeeBeans
* GroundCoffee
* Recipe
* Coffee

⠀Примеры правил (инвариантов):
* amount must be positive
* temperature must be between 0 and 100
* recipe cannot exist with invalid values

⠀👉 **Если удалить UI, Application и Infrastructure — домен всё равно имеет смысл.**
Это главный критерий домена.

## Инварианты (ключевая идея домена)
**Инвариант — это правило, которое всегда должно быть правдой.**
Если инвариант нарушен:
* объект **не имеет права существовать**
* система должна **отказаться принять такое состояние**

⠀Поэтому:
* инварианты живут в конструкторах
* проверяются один раз
* дальше считаются гарантированными

⠀
## Entity vs Value Object
### Value Object — “что”
* не имеет идентичности
* определяется значениями
* immutable
* два объекта с одинаковыми значениями — эквивалентны

⠀Примеры:
* Water
* Recipe
* Coffee

⠀Entity — “кто”
* имеет идентичность
* может менять состояние
* остаётся “тем же самым объектом”

⠀В нашей модели **Entity почти нет**, и это нормально. Модель может быть почти полностью VO.

## 2️⃣ Application (Use Cases)
## Что такое Application слой
**Application — это сценарии.** Он отвечает на вопрос:
*“Что система делает шаг за шагом?”*
Это **не бизнес-понятия**, а **бизнес-процессы**.

## CoffeeMachine — почему это НЕ домен
### prepare(recipe):
###   take water
###   take beans
###   grind
###   heat
###   calculate strength
###   send coffee
Этот код:
* координирует несколько объектов
* не имеет собственных инвариантов
* описывает **как**, а не **что**

⠀👉 Значит это **Use Case / Application Service**, а не домен.

## Inbound Port (вход в систему)
Inbound port отвечает на вопрос:
*“Что внешний мир МОЖЕТ попросить систему сделать?”*
Пример:
* PrepareCoffeePort

⠀UI видит **только порт**, а не реализацию.

## 3️⃣ Ports & Adapters (Hex)
## Зачем нужны порты
**Порты фиксируют границу.**
Они отвечают на вопрос:
*“Через что внешний мир может со мной разговаривать?”*
Порты:
* защищают application от UI
* защищают domain от infrastructure
* не дают системе “расползтись”

⠀
## Outbound Ports (выход из системы)
Outbound port — это **зависимость application от мира**.
Примеры:
* WaterSourcePort
* BeanSourcePort
* GrinderPort
* HeaterPort
* CoffeeReceiverPort

⠀Application **не знает**, откуда реально берётся вода. Он знает только: *“я могу запросить воду”*.

## Adapters (Infrastructure)
**Адаптер — это реализация порта.**
Он:
* переводит язык application → язык конкретного устройства
* не содержит бизнес-логики
* легко заменяется

⠀Примеры:
* WaterTankAdapter
* CupAdapter

⠀Если завтра вода будет идти из водопровода, меняется **адаптер**, а не application.

## 4️⃣ Infrastructure
Infrastructure — это:
* устройства
* внешние системы
* детали реализации

⠀Примеры:
* WaterTank
* BeanContainer
* Grinder
* Heater
* Cup

⠀👉 **Это самый заменяемый слой.** Он всегда должен быть снаружи.

## 5️⃣ UI
## Что такое UI в архитектурном смысле
UI — это **входной адаптер**.
Он:
* принимает действия пользователя
* переводит их в вызовы inbound ports
* не содержит бизнес-логики

⠀
## Почему Builder живёт в UI
Пользователь:
* действует пошагово
* может вводить неполные данные
* может менять решения

⠀Домен:
* не принимает “полусобранные” объекты

⠀👉 RecipeBuilder — это **адаптер между человеком и доменом**.

## 6️⃣ Ошибки (очень важно)
## DomainValidationError
**“Такой объект не может существовать.”**
* нарушение инварианта
* ошибка создания Value Object
* не имеет смысла повторять операцию

⠀Пример:
* water amount ≤ 0

⠀
## DomainError
**“Объект валиден, но операция невозможна сейчас.”**
* не хватает воды
* не хватает зёрен
* ожидаемая ситуация

⠀Операцию можно повторить позже.

## UI Errors
* кнопка недоступна
* рецепт не собран
* неверный шаг

⠀👉 UI **не должен показывать stack trace**. Он должен показывать **понятный результат**.

## 7️⃣ Почему hex-архитектура — это хорошо
Hex даёт:
* 🔒 жёсткие границы
* 🔁 заменяемость деталей
* 🧠 ясную модель
* 📈 возможность роста
* 🧪 тестируемость (даже если ты не пишешь тесты)

⠀Самое важное:
**Изменения локализуются.**

## 8️⃣ Короткий итог (один абзац)
Домен описывает *что есть что*. Application описывает *что делать*. Порты описывают *как можно общаться*. Адаптеры описывают *как именно это сделано*. UI переводит действия человека в команды. Infrastructure — заменяемая деталь.
Если ты это понимаешь — ты понимаешь **hex-архитектуру**.
